# 国特答辩追问库

## 技术价值

**1. 这是不是给大模型套了一个页面？**

不是。核心增量在受治理的知识链：型号过滤后的 pgvector/pg_trgm 双路召回、RRF 融合、结构化 Agent 工具协议、图谱来源追溯、审核发布与回滚，以及自动化证据链。模型只是可替换的生成组件。

**2. 相比普通 RAG 的创新是什么？**

普通 RAG 是一次检索后生成；本系统让 Agent 在手册、案例、图谱和设备历史间交叉验证，同时约束至少两类成功工具，并记录每个动作的参数、状态和耗时。

**3. 为什么需要知识图谱？**

向量检索擅长相似文本，图谱明确表达故障、原因和措施的方向关系。两者互补，图谱边还保留案例来源、证据文本、审核状态和版本。

## 检索与评测

**4. 为什么使用 RRF？**

向量分数与 trigram 相似度不在同一量纲，直接加权容易受分数分布影响。RRF 只融合排名，对专有型号和语义改写更稳，并可做 vector、lexical、hybrid 三组消融。

**5. 如何证明检索效果？**

20 个专家事实各做 10 种受控改写，共 200 查询；同一脚本输出 Recall@5、MRR、nDCG、型号过滤准确率和 P50/P95，原始逐条结果保留为 JSON。

**6. 为什么不是 PostgreSQL 全文检索？**

中文分词配置会引入额外词典和部署差异，当前选择 pg_trgm 做字面召回，重点覆盖型号、故障码和专有词；生产数据上的消融报告决定后续是否引入中文分词器。

**7. SQLite 和 PostgreSQL 结果一致吗？**

召回语义一致，都是向量与字面双路候选加 RRF；执行方式不同。SQLite 是小规模回退，生产性能和最终指标只以 PostgreSQL + pgvector 为准。

**8. 引用准确率怎么计算？**

评测同时检查引用的 chunk/doc 是否真实存在、内容是否与数据库一致，以及报告中的 `[E#]` 是否落在实际引用范围内，避免只有编号没有来源。

## Agent 与可信性

**9. 如何防止 Agent 随意调用工具？**

动作必须通过 Pydantic 协议校验；工具名、输入结构、最大迭代次数、解析重试、调用预算和最少工具多样性均由服务端约束。

**10. 工具失败会怎样？**

异常被转换为结构化失败动作，不会让未初始化数据进入报告；SSE 始终发终止事件，客户端不会永久等待。失败路径有自动化故障注入测试。

**11. 为什么不展示完整思维链？**

产品只展示可审核的行动理由、工具、观察摘要和证据，不依赖或暴露模型私有思维链。评审重点是可复现动作与证据。

**12. 置信度可靠吗？**

当前是基于证据数量、来源多样性、图谱和引用覆盖的可解释评分，不宣称为统计校准概率。完成标注校准前统一使用“评分”表述。

## 安全与治理

**13. 如何防提示注入和知识投毒？**

入库前检测疑似提示注入并拒绝；生成提示明确知识片段是不可信数据；一线修正先进入待审影子库，审核发布后才全局生效，并支持回滚与审计。

**14. 高风险检修建议如何处理？**

系统识别高压、带电、带压、高温等类别，明确要求停机、隔离和人工确认。它提供知识辅助，不替代持证人员和安全规程。

**15. 图谱错误如何追责？**

每条关系能回溯来源案例、证据文本、抽取方法、评分、审核状态和版本；实体别名单独记录归一方式。

## 国产化与工程

**16. 如何证明适配龙芯和银河麒麟？**

不是靠架构分析结论，而是在目标机运行采集脚本，保留 `uname/lscpu/os-release`、依赖检查、服务日志、SBOM、制品哈希和 8 小时健康记录。

**17. 最大兼容风险是什么？**

主要是 pydantic-core、pgvector 和本地 ONNX 依赖。生产侧用纯 Python pg8000、纯净 uvicorn 和云端嵌入规避大部分风险；剩余原生组件必须用实机编译记录证明。

**18. 为什么生产必须用 pgvector？**

应用层全量余弦无法支撑规模化 Top-K。pgvector 用 HNSW 在数据库内近邻召回，配合型号前置过滤和 pg_trgm 候选，SQLite 只保留为演示回退。

**19. 数据如何备份恢复？**

脚本生成 PostgreSQL custom-format 备份、SHA256 和内容清单；恢复验证只允许显式指定独立测试库，并拒绝覆盖源库，恢复后核验关键表行数。

**20. 当前还有哪些边界？**

真实 pgvector 指标、30 并发生产结果、LoongArch 8 小时记录和模型 Agent 完成率必须在对应环境采集。仓库已经提供自动化脚本，但没有实测就不会宣称达标。
